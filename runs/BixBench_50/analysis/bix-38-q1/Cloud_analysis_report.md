# Cloud audit report: bix-38-q1

Independent read-through/audit-of-the-audit of the existing `history_analysis.md` for this task. Written retrospectively; no agent code was rerun, no Galaxy API was called, and no hidden reference/answer key was opened. This document follows `HISTORY_ANALYSIS_INSTRUCTIONS.md` Section 9.

## 1. Task, experimental design, evidence availability, matching rules

- Task: `bix-38-q1` (bixbench). Prompt (from `bix-38-q1.json` and confirmed in `history_analysis_evidence.json:.task.prompt`): "What is the fold-change in median tree length between fungi and animals after calculating tree lengths with PhyKIT?" Input specification: `phylobio/BixBench-Verified-50`; `hidden_reference_included: false`.
- Evidence source: a supplied workbook (`bixbench_execution_condition_links.xlsx`, sha256 recorded in `run_manifest.json`). This is an observed-link inventory, not an independent protocol manifest; `experimental_design.coverage_status = "unknown_protocol_inventory"` in the evidence JSON, matching the report's own statement that "expected coverage and replicate matching are unknown."
- 30 runs are recorded (`run_manifest.json.observed_rows` has 30 entries; `history_analysis_evidence.json.runs | length` = 30). Two conditions (`galaxy`, `open_ended_code`) x five model labels (Codex GPT-5.5, Codex GPT-5.6 Sol, Codex GPT-5.6 Luna, DeepSeek V4 Pro via Codex, DeepSeek V4 Pro via Claude Code [superseded]) x three replicates = 30. All 30 rows have `status: "trace_observed"`.
- Model identity: labels are supplied/observed, not independently runtime-verified beyond the label itself (the route table's "Runtime model ID" column repeats the supplied label; no separate verification field was found flagged `true` in the sampled run records).
- Replicate numbers (`r1`/`r2`/`r3`) are explicitly documented as labels, not matched seeds (`experimental_design.seed_availability = "not_collected"`).

## 2. Main outcomes (kept separate)

- **Official accuracy/evaluator score**: all 30 runs carry an `outcome.original_evaluator_score` (field name `accuracy.score`, mode `llm_verifier_auto_code`), and all 30 sampled values equal 1.0 (confirmed on run 1; `finding_accuracy` in the evidence JSON reports numerator=30/denominator=30 "scores retrieved", not "scores equal to 1" — the claim is about coverage, and the per-model comparison table separately shows `galaxy_mean = code_mean = 1.0` for every one of the five models).
- **Observed execution**: retrieved public Galaxy histories expose 33 distinct analytical creating jobs total (deduplicated by native job ID) across the 15 Galaxy-condition runs, with 0 recorded as failed/error. This is separate from shell/MCP call counts (e.g., run `galaxy_codex_gpt_5_5_r1` alone shows 19 completed shell calls, 9 MCP calls, but only 1 analytical Galaxy job).
- **Auditor interpretation**: the report is explicit that a fixed answer score of 1.0 in all conditions/models, combined with 0 failed jobs, is a case-study descriptive result for one task — it does not establish Galaxy/open-ended-code equivalence, superiority, or benchmark-wide reliability. I concur with this framing; the underlying evidence JSON (`comparisons[]`) reports all score differences as `0.0 percentage points` with `status: "descriptive_only"`, consistent with that restraint.

## 3. Manuscript Results-section walkthrough

**Accuracy and output agreement.** All 30 runs have the same `accuracy.score` field and all equal 1.0 in both conditions for all five models (verified by re-reading run 1 and by the `comparisons[]` array's `galaxy_mean`/`code_mean` = 1.0 for all five `score_*` comparison records). This is a within-task, same-metric comparison; it is not pooled across benchmarks. Nothing in my spot-check disagreed with the report on this point.

**Execution, failures, recovery.** History-level job counts and per-run failure counts in the route table were checked against `derived_metrics` in the evidence JSON for a full run of the Codex GPT-5.5 group and match exactly: `analytical_job_count` = 1, 1, 3 for `r1`/`r2`/`r3` (table: 1/0, 1/0, 3/0), `total_failed_jobs` = 0 for all three, and `nonzero_exit_shell_calls` = 1, 0, 1 (table's "Nonzero shell calls" column: 1, 0, 1). Summing `analytical_job_count` across all 15 Galaxy runs by model group (5+7+8+7+6, from the route table) equals 33, matching the reported total. `open_ended_code` runs have `analytical_job_count: null` (not zero) because Galaxy job telemetry is not applicable to that condition — the report's "unavailable" label in the route table is consistent with this, not a silently-dropped zero.

**Solution-route variability.** The report lists PhyKIT as the common tool family across nearly all runs, with a subset of `open_ended_code` runs (and one Galaxy Luna run) additionally showing a "Newick/branch parser" or "Datamash" indicator. This is descriptive cataloguing, not a claim of scientific equivalence between routes; `finding_variability` in the evidence JSON has `numerator/denominator/estimate = null`, correctly leaving this unquantified rather than inventing a diversity statistic.

**Token cost, provenance, readability.** The five reported Galaxy/code median input-token ratios (2.32, 3.4, 3.35, 1.07, 2.14) were recomputed from `comparisons[]` and match to two decimal places: 2.316 (codex_gpt_5_5), 3.398 (codex_gpt_5_6_luna), 3.348 (codex_gpt_5_6_sol), 1.075 (deepseek_v4_pro_via_claude_code_superseded), 2.137 (deepseek_v4_pro_via_codex). All five are ratios of condition medians (not median-of-ratios), as the report states. No human-readability measurement exists; the report correctly declines to claim one.

No disagreement was found between `history_analysis.md` and `history_analysis_evidence.json` on any of the four sections for the items checked.

**Additional unsurfaced field.** All 15 Galaxy-condition runs carry a secondary `outcome.step_completion.score = 0.5` (`passed: false`), with a `fresh_galaxy_history_recorded: false` step failing while `final_deliverable_written: true` passes; the 15 `open_ended_code` runs instead score `step_completion.score = 1.0` (`passed: true`) on a different step codebook (`agent_run_completed`, `final_deliverable_written`). This is a distinct, auditor/repository-defined completion checklist, separate from the original `accuracy.score` evaluator field discussed above, and `history_analysis.md` does not mention it. It should not be read as a second accuracy measure — it appears to track whether a *fresh* Galaxy history was recorded during the run, which is false for all 15 Galaxy runs in this task's evidence. This is worth flagging as an open question rather than resolving it here, since the step-completion codebook's provenance and pass/fail criteria are not documented in the reviewed files.

## 4. Per-condition/model/replicate route table

The 30-row table in `history_analysis.md` Section 4 was spot-checked against the evidence JSON for the Codex GPT-5.5 model group (6 runs) and one additional Galaxy record (`galaxy_codex_gpt_5_6_luna_r1`), covering score, job counts, and shell-call counts. All checked cells matched exactly (see Section 3 above for figures). I did not re-derive the remaining 24 rows cell-by-cell; no discrepancy was found in the sampled rows, and the aggregate 33-job total is consistent with summing the table's own "Galaxy analytical jobs" column, which is an internal-consistency check in itself.

## 5. Input sharing, external computation, environment/reproducibility

- `input_manifest.json` shows per-run input-file counts and SHA-256 values copied from the original run-reported trace manifests (`inputs_manifest.json` per run), not rehashed by this audit (`"note": "Hashes are copied from original trace manifests; full staged inputs were not rehashed by this audit"`). All 20-file input sets for the Codex/DeepSeek-via-Codex open-ended runs and most Galaxy runs share an identical SHA-256 (`bb5b8d7a22...`), while the three DeepSeek-via-Codex and three DeepSeek-via-Claude-Code(superseded) Galaxy runs show `count: 0` inputs with a distinct hash (`c1695013...`) — a real asymmetry worth surfacing: the Galaxy condition for those two model groups recorded zero staged inputs in the manifest snapshot, versus 20 for their open_ended_code counterparts. `history_analysis.md` does not call this out explicitly; it is visible only by reading `input_manifest.json` directly. This is not necessarily an error (Galaxy runs may stage inputs via API upload rather than a local `inputs_manifest.json`), but it is an unexplained condition-level asymmetry that the existing report does not flag.
- `recovered_code/` contains only an `open_ended_code/` subdirectory (16 run folders, `.command.txt` files); there is no `recovered_code/galaxy/` subdirectory. This is consistent with Galaxy jobs being API-driven (captured instead in `job_ledgers/galaxy/*.json`) rather than shell-recoverable, and is implicitly explained by the recovered-code manifest's `"execution_claim": "Archival extraction only; no recovered code executed"` scope (which only lists `open_ended_code` items). `selected_outputs/open_ended_code/manifest.json` explicitly states `"status": "not_collected", "reason": "Trace output files are retained in source_snapshots; no code was replayed"` — this gap is documented, not silent.
- `selected_outputs/galaxy/` contains 15 per-history directories with `.dat` byte snapshots, one per Galaxy run's underlying history ID (matches the 15 Galaxy-condition runs).
- Two `.dat` sample files per history were not opened for content (out of scope; this is a file-presence inventory check, not a byte-level content audit).
- The audit record itself documents a real limitation: `audit.limitations` states TLS certificates were not verified on the source host because "the host proxy presented an invalid certificate," so retained-byte hashes do not authenticate the remote server. This is disclosed in the evidence JSON and should be treated as a standing caveat on all retrieved Galaxy bytes for this task.

## 6. Verification methods (what was checked / not checked)

Checked: `ls -la` directory listing; full read of `README.md`, `history_analysis.md` (current version only, not `.v1`/`.v2`), `run_manifest.json`, `input_manifest.json`, `bix-38-q1.json`; `jq` queries against `history_analysis_evidence.json` for `.runs | length`, `.audit`, `.task`, `.experimental_design`, `.manuscript_findings`, `.comparisons`, and per-run `{run_id, condition, model, status, outcome}` and `{run_id, derived_metrics}` (sampled the Codex GPT-5.5 group plus one Luna run); `find` inventory of `job_ledgers/`, `recovered_code/`, `selected_outputs/`, `source_snapshots/` to at least depth 3; head/full read of `recovered_code/manifest.json`, one sample `.command.txt` file, one sample Galaxy `job_ledgers` file, one sample `open_ended_code` `job_ledgers` file, and both `selected_outputs` manifest files.

Not checked (explicitly out of scope): full byte-level hash reverification of any `.dat` output or trace file; full transcript replay of any of the 30 runs; execution of any recovered command or Galaxy job; opening of the hidden BixBench answer key; cell-by-cell re-derivation of all 30 route-table rows (6 of 30 rows were directly verified against evidence-JSON fields); TLS/server-identity verification (already flagged as unverifiable by the original audit itself).

## 8. Missing evidence / open gaps

- No independent experiment manifest exists to confirm 3 replicates were the intended/complete design rather than an observed subset; coverage remains formally "unknown."
- The zero-input-count records for the two DeepSeek-via-* Galaxy model groups are not explained anywhere in `history_analysis.md`. A `seed_history.json` file is present in `source_snapshots/huggingface_traces/files/` for every one of the 15 Galaxy runs (including these six), suggesting Galaxy runs may start from a pre-seeded/shared history rather than a fresh per-run upload; this is a plausible explanation but was not independently confirmed by opening and parsing those files, so it remains a documented lead rather than a resolved finding. It is also consistent with the `step_completion` step `fresh_galaxy_history_recorded: false` noted above for all 15 Galaxy runs.
- The `outcome.step_completion` codebook (`fresh_galaxy_history_recorded`, `agent_run_completed`, `final_deliverable_written`) and its `0.5`/`1.0` scoring are not documented in `history_analysis.md`, `README.md`, or the manifests reviewed; its authorship (original evaluator vs. repository pipeline vs. auditor-derived) is unresolved from the files read.
- No seed information, no independently defined task-difficulty label, and no human-readability assessment are available, matching the report's own stated gaps.
- Full-byte reverification of `.dat` outputs and TLS-authenticated retrieval were not performed by this audit or the original one.

### Abstract-ready paragraph

For bixbench task bix-38-q1, 30 supplied runs (2 conditions x 5 model labels x 3 replicates) were audited retrospectively. All 30 runs carried an original `accuracy.score` of 1.0, with no score difference recorded between the Galaxy and open_ended_code conditions for any of the five model groups. Retrieved public Galaxy histories exposed 33 distinct analytical creating jobs across the 15 Galaxy-condition runs, of which 0 were recorded as failed. Galaxy/code median input-token ratios ranged from 1.07 to 3.40 across the five model groups, computed as ratios of condition medians. These figures were independently confirmed against `history_analysis_evidence.json` and describe this single task only; they do not establish a benchmark-wide effect of condition on accuracy or cost.
