# bix-28-q3 independent audit-of-the-audit

This document is an independent spot-check of the existing `history_analysis.md` / `history_analysis_evidence.json` package for task `bix-28-q3`, produced per `HISTORY_ANALYSIS_INSTRUCTIONS.md`. It is retrospective only: no agent code was rerun, no live Galaxy API was called, and no hidden reference/answer key was opened. All numbers below were either read directly from `history_analysis_evidence.json` via `jq`, or computed from raw per-run fields in that file using `jq`/shell arithmetic (auditor actions, per Section "Scope boundaries" of the instructions).

## 1. Task, experimental design, evidence availability, and matching rules

- Benchmark/task: `bixbench` / `bix-28-q3`. Prompt (from `bix-28-q3.json` and confirmed in `history_analysis_evidence.json:.task.prompt`): "Using PhyKIT to calculate long branch scores, what is the median long branch score for the fungal gene 996662at2759?" `hidden_reference_included: false` in `bix-28-q3.json`.
- Source dataset: `phylobio/BixBench-Verified-50`.
- Inventory source: a supplied workbook (`run_manifest.json:.inventory_source`, `/Users/4475918/Downloads/bixbench_execution_condition_links.xlsx`), not an independent protocol manifest. `run_manifest.json:.expected_coverage = "unknown_without_independent_protocol"`, and `history_analysis_evidence.json:.experimental_design.coverage_status = "unknown_protocol_inventory"`. This is consistent — expected coverage is explicitly unknown, not silently assumed.
- Runs present: 30 observed rows in `run_manifest.json` (verified: `jq '.observed_rows | length'` → 30) and 30 run records in `history_analysis_evidence.json` (verified: `jq '.runs | length'` → 30). Both files agree.
- Two conditions are present and kept distinct throughout: `galaxy` and `open_ended_code` (labelled "Galaxy-API code with skills" and "Open-ended code with skills" respectively in `run_manifest.json`). 15 galaxy runs, 15 open_ended_code runs (3 replicates × 5 model labels × 2 conditions).
- Model labels present: Codex GPT-5.5, Codex GPT-5.6 Sol, Codex GPT-5.6 Luna, DeepSeek V4 Pro via Codex, DeepSeek V4 Pro via Claude Code (superseded). These are supplied labels; `history_analysis.md` reports runtime model IDs (e.g. `gpt-5.5`) only where a retrieved invocation file verifies them.
- Replicate matching: `history_analysis_evidence.json:.experimental_design.matching_rule` states replicate numbers are labels, not matched seeds; `seed_availability: "not_collected"`. No independent protocol manifest exists to establish expected replicate counts beyond the 3 observed per cell.
- Known confounders recorded (`experimental_design.known_confounders`): condition-specific prompts/tools, possible container-revision differences, possible shared source histories.
- Galaxy-side evidence: public Galaxy history contents were retrieved for 15 distinct histories (verified independently: `find selected_outputs/galaxy -maxdepth 1 -type d | tail -n +2 | wc -l` → 15, and the same count under `source_snapshots/galaxy`), one per galaxy-condition run (15 galaxy runs → 15 histories, no sharing detected in this count).
- Unverifiable/unknown items, stated explicitly rather than guessed: independent replicate/seed protocol, TLS server authentication for retrieved sources (`audit.limitations` notes the host proxy presented an invalid certificate, so retained-byte hashes do not authenticate the remote server), and task difficulty (unclassified, no independent source supplied).

## 2. Main outcomes (kept visibly separate)

**(a) Official accuracy/evaluator score, as recorded.** All 30 runs carry an `original_evaluator_score` under the field name `accuracy.score` (verified via `jq -r '.runs[] | [.run_id, .outcome.original_evaluator_score] | @tsv'`). 29/30 runs scored 1.0; one run, `galaxy_codex_gpt_5_6_sol_r1`, scored 0.0 with submitted answer `146.3023` (all other runs submitted answers in the `-30.4550x` range for the same question). This is the evaluator's own field, not an auditor regrade; the auditor did not open a hidden answer key and cannot independently confirm the ground truth, only that the evaluator recorded this score for this submitted answer.

**(b) Observed execution facts, as recorded.** Retrieved public Galaxy histories expose 48 distinct analytical creating jobs across the 15 galaxy-condition runs, of which 1 has failed/error status (verified: `jq '[.runs[] | select(.condition=="galaxy") | .derived_metrics.analytical_job_count] | add'` → 48; `jq '[.runs[] | select(.condition=="galaxy") | .derived_metrics.total_failed_jobs] | add'` → 1). These are raw job counts from Galaxy job records, distinct from shell/MCP tool-call counts, and distinct from "scientific attempts."

**(c) Auditor interpretation (labelled as such).** The single scored-0 run (`galaxy_codex_gpt_5_6_sol_r1`) is also the run carrying the one recorded failed Galaxy job (`analytical_job_count=4`, `total_failed_jobs=1`) among the runs I inspected in the raw evidence. Co-occurrence of a failed job and an incorrect submitted answer in the same run is an association I observed in the data, not a demonstrated causal link — the instructions caution against inferring scientific correctness from job-level success/failure alone, and I did not trace the recovery/analytical chain in enough depth to determine whether the wrong answer (`146.3023`, an order of magnitude different from the ~-30.455 value returned everywhere else) originated from the failed job, a parameter error, or a separate misinterpretation step. This remains an open question for deeper case review, not a finding.

## 3. Manuscript Results-section walkthrough for this task

### Accuracy and output agreement (Section 4)
`history_analysis.md`'s table reports, per model label: Galaxy mean / code mean / difference / token ratio. I recomputed all five rows directly from `history_analysis_evidence.json:.comparisons[]` and, for two of the five (codex_gpt_5_5, codex_gpt_5_6_sol), from the raw per-run `usage.provider_reported_input_tokens` values. All five score-mean pairs and all five token ratios matched the document exactly: codex_gpt_5_5 (1/1, ratio 3.73), codex_gpt_5_6_luna (1/1, ratio 4.59), codex_gpt_5_6_sol (0.667/1, ratio 2.17), deepseek_v4_pro_via_claude_code_superseded (1/1, ratio 2.02), deepseek_v4_pro_via_codex (1/1, ratio 4.04). No discrepancy found. All comparisons carry `status: "descriptive_only"` and `uncertainty: null` — no equivalence or superiority claim is made, consistent with the single-task, unmatched-seed design. What is unresolved: whether "accuracy.score" is a binary correctness flag or a continuous evaluator score is not stated in the evidence beyond the field name and `original_evaluator_mode: "llm_verifier_auto_code"`; the document appropriately does not claim more than "original numeric evaluator score."

### Analysis execution, failures, and recovery (Section 5)
The document's headline figures (48 distinct analytical creating jobs, 1 failed job) reproduce exactly from `manuscript_findings[1]` (`finding_execution`: numerator 1, denominator 48) and from summing `derived_metrics.analytical_job_count` / `total_failed_jobs` across the 15 galaxy runs. Per-run job/failure counts in the route table (Section 4 of `history_analysis.md`) were checked row-by-row against `derived_metrics.analytical_job_count` and `derived_metrics.total_failed_jobs` for all 15 galaxy runs, and nonzero-shell-call counts were checked for all 30 runs against `derived_metrics.nonzero_exit_shell_calls`. All 15+15 values matched exactly; no discrepancy found. Unresolved: `failed_jobs_before_first_supported_result` and `failed_attempts_before_first_correct_answer` are `null` in every run I inspected — the document does not claim these, correctly leaving the "failures before result" ordering unresolved. The document labels a later same-tool/same-input successful job as a recovery "candidate," not a confirmed recovery, which matches the instructions' caution against inferring recovery from a later success alone.

### Solution-route variability (Section 6)
The route table lists tool-family indicators (PhyKIT, Newick/branch parser, IQ-TREE report) per run. I confirmed via the raw event list for `galaxy_codex_gpt_5_5_r1` that PhyKIT-named Galaxy tool IDs (`toolshed.g2.bx.psu.edu/repos/goeckslab/phykit_metrics/phykit_metrics/0.2.0+galaxy0`, and a second candidate tool `toolshed.g2.bx.psu.edu/repos/padge/phykit/phykit_tree_based/0.1.0`) appear as real `analysis`-type events with `execution_location: "galaxy_job"`, not placeholders. `finding_variability` in the evidence JSON has `numerator/denominator/estimate: null`, consistent with the document's own statement that it only catalogues indicators and does not assert biological equivalence across routes. Task difficulty is explicitly unclassified in both the document and the evidence; this question is correctly marked not assessable for this task rather than answered by proxy (e.g., token count or score).

### Token cost, provenance, and readability (Section 7)
Token ratios (Section 2 table) are stated as ratios of condition medians, not medians of paired ratios; I confirmed this definition against `comparisons[].estimate_unit = "ratio of condition medians"` and reproduced the codex_gpt_5_6_sol ratio (2.17) by hand from the three galaxy and three open_ended_code `provider_reported_input_tokens` values (medians 1,110,893 vs 511,327 → 2.173). No discrepancy found. No human-readability measurement exists for this task, and the document does not claim one — it only claims "provenance inspection," which is the correct restrained framing under Section 7 of the instructions (structured manifests support inspectability, not measured faster review).

## 5. Input sharing, external computation, and reproducibility notes

`input_manifest.json` reports run-level input counts from staged trace manifests (not independently rehashed by this audit — the file states this itself: `"note": "Hashes are copied from original trace manifests; full staged inputs were not rehashed by this audit"`). One notable pattern I observed directly in `input_manifest.json`: the three `galaxy_deepseek_v4_pro_via_codex_*` and three `galaxy_deepseek_v4_pro_via_claude_code_superseded_*` galaxy runs each show `"count": 0` for their `inputs_manifest.json`, with a different SHA-256 (`c1695013...`) than the 20-input, `bb5b8d7a...`-hash manifest shared by every other run (all `codex_gpt_5_5`/`gpt_5_6_*` runs, and all `open_ended_code` runs including the two deepseek model's open_ended_code counterparts). This is a real asymmetry between the galaxy-condition and open_ended_code-condition input manifests for exactly these two model labels, and it is not called out explicitly in `history_analysis.md`. It may reflect a difference in how the galaxy harness stages/records inputs (e.g., via seed-history copy rather than a local `inputs/` directory — the job-ledger excerpt for `galaxy_codex_gpt_5_5_r1` shows a `copy_history` call against a seed history, which is a plausible mechanism, but this is my inference, not a confirmed explanation) rather than an absence of inputs; I did not verify this further and flag it as an open item (Section 8). External computation: Galaxy-hosted PhyKIT jobs use a Galaxy toolshed tool ID (`toolshed.g2.bx.psu.edu/repos/goeckslab/phykit_metrics/...`), i.e. Galaxy-hosted execution, per the sampled event trace. Reproducibility limits: `audit.limitations` records that TLS certificates were not verified for retrieved sources ("the host proxy presented an invalid certificate"), so retained-byte hashes do not authenticate the remote server; this applies to all 45 `sources` entries, not selectively.

## 8. Missing evidence / open gaps specific to this task

- No independent protocol manifest exists to confirm 3 replicates per model/condition was the intended design rather than an artifact of what the workbook happened to link; `run_manifest.json` and the evidence JSON both label expected coverage unknown, appropriately.
- The single scored-0 run (`galaxy_codex_gpt_5_6_sol_r1`) has an unresolved failure chain: whether the recorded failed Galaxy job caused the anomalous submitted answer (`146.3023` vs. the ~`-30.455` value elsewhere) is not established by any field in the evidence I inspected (`failed_jobs_before_first_supported_result` is null for this run). This would require a deeper, still-retrospective read of that run's full event trace, which I did not perform.
- No `recovered_code/galaxy/` directory exists even though several galaxy-condition runs report nonzero shell calls (e.g., `galaxy_codex_gpt_5_6_sol_r2/r3`, `galaxy_codex_gpt_5_6_luna_r2/r3`, `galaxy_deepseek_v4_pro_via_codex_r1/r3`). `recovered_code/manifest.json` only documents scope as "Only recognizable command strings and Python heredocs extracted" and only contains `open_ended_code` items; it does not explicitly state why no galaxy-side shell commands were extracted despite nonzero exit codes being recorded for galaxy runs. This is a documentation gap worth flagging, not necessarily an error, since the underlying shell events for galaxy runs are still present in the job ledgers (as seen in the sampled `galaxy_codex_gpt_5_5_r1` ledger) even though they were not separately materialized as `.command.txt` files.
- The asymmetric `input_manifest.json` counts (0 vs 20) for the two DeepSeek-model galaxy runs (Section 5 above) are not explained anywhere in `history_analysis.md`, `run_manifest.json`, or `input_manifest.json` itself beyond the generic rehashing-not-performed note. Root cause (different staging mechanism vs. a genuine evidence gap) is unresolved.
- Task difficulty remains unclassified; no independently defined difficulty source was supplied for this task, so Section 6 questions about difficulty-linked variability cannot be assessed here.
- No human-readability evaluation exists for this task; per Section 7 of the instructions, this must be reported as an absent experiment, not estimated.

### Abstract-ready paragraph

For bixbench task bix-28-q3, I independently verified 30 observed runs (15 Galaxy, 15 open-ended code, across 5 model labels × 3 replicates) in both `run_manifest.json` and `history_analysis_evidence.json`. All 30 runs carry an original evaluator score under the field `accuracy.score`: 29 of 30 scored 1.0, and one Galaxy-condition run (`galaxy_codex_gpt_5_6_sol_r1`) scored 0.0. Retrieved public Galaxy history records for the 15 Galaxy-condition runs expose 48 distinct analytical creating jobs, of which 1 has failed/error status — both figures reproduced exactly by summing per-run `derived_metrics` fields and by reading the corresponding `manuscript_findings` record. I hand-verified one Galaxy/open-ended-code input-token median ratio (codex_gpt_5_6_sol: 1,110,893 vs. 511,327, ratio 2.17) directly from raw per-run token totals, matching the pre-computed value in the evidence file. These are single-task, unmatched-replicate observations and do not establish a benchmark-wide Galaxy-versus-open-ended-code effect.
