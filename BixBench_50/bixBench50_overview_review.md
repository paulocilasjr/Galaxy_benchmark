# Scientific Review of the BixBench-50 Results

The original overview was not publication-ready. Its principal descriptive totals were correct, but several conclusions exceeded the evidence, the comparison design was incompletely described, and uncertainty was absent. The revised [Results section](bixBench50_overview.md) is a more defensible retrospective account. It cannot, by itself, establish the four originally proposed claims or guarantee suitability for Nature Methods.

## Findings and Corrections

1. **Major: the pooled accuracy difference did not establish a Galaxy benefit or preservation of accuracy in an equivalence sense.** The verified counts are 639/750 accepted answers in Galaxy and 615/750 in open code. Runs are nested within questions, and the 50 questions come from 33 capsules; treating all 1,500 observations as independent would misrepresent the design. An added, explicitly post hoc capsule bootstrap gives an exploratory 95% interval of -1.41 to +7.91 percentage points for the +3.2-point difference. The interval crosses zero, and no non-inferiority margin was specified. Both conditions used skills, prompts and tools differed, and GPT-5.5 container versions varied by condition. The largest difference came from the superseded DeepSeek/Claude Code configuration, which accounts for 16/24 of the additional accepted Galaxy answers. Excluding that configuration reduces the descriptive gap to +1.33 points. The revision reports high observed acceptance without claiming causation, superiority or equivalence.

2. **Major: answer acceptance was conflated with scientific correctness and successful Galaxy-only execution.** Binary evaluator acceptance does not validate the entire method, parameters or provenance. The original evaluator marked `fresh_galaxy_history_recorded` false for all 750 Galaxy runs, whereas the audit retrieved dataset-bearing histories for 714 run records. This discrepancy is unresolved: neither an evaluator bookkeeping defect nor execution noncompliance can be assumed from these records alone. Five Galaxy and one open-code record lacked a collected submitted answer and already had original scores of zero; these were retained, not newly imputed. The revision separates the answer endpoint from execution checks and does not certify an exclusively Galaxy-derived solution count. Evidence: the `outcome`, `evidence_completeness` and `events` fields in the task evidence files, cross-checked against each archived `evaluation.json`.

3. **Major: the readability and cost-effectiveness claims were unmeasured.** No blinded reader assessment, review-time measurement, error-detection study, reproducibility rerun or cost-effectiveness analysis supports the original statements that Galaxy improves human readability or that its benefits generally justify the token cost. Open code also had archived transcripts and outputs; describing it as necessarily transient overstates the contrast. The revision reports the presence of structured Galaxy provenance and explicitly identifies human-review benefit as unmeasured. The original fourth subsection title was changed because it asserted an untested outcome.

4. **Major: a causal explanation of token overhead was not supported.** The reported task-level correlations reproduce (input-token ratio versus recorded jobs: Pearson r = 0.152; versus error-state jobs: r = -0.102; n = 50 questions). These ecological correlations do not separate retry costs from orchestration costs, account for differences in task complexity, or rule out nonlinear associations. Job counts and shell exits also measure different units. The revised Results omit the causal interpretation and state that stage-level attribution is unavailable. More relative token use did not consistently accompany greater answer acceptance; no independent capability ranking was supplied.

5. **Major: route labels could not establish model-dependent scientific solution diversity.** The high-level classification was absent for 76.3% of Galaxy runs and scientifically unclassified for 81.3% of open-code runs. Labels are non-exclusive and selectively recognize some families, notably phylogenetic tools. They are neither a comprehensive method taxonomy nor an unbiased diversity measure. Different wrappers can implement the same calculation, while the same family label can conceal different inputs or parameters. No independent difficulty strata were supplied. The revision replaces qualitative claims about the broadest mix or greater variability with exact recorded-label counts and bounded case examples.

6. **Moderate: token aggregation and accounting needed clarification.** The overall 4.74-fold median ratio and 2.45-9.62 interquartile range reproduce. Each observation is a ratio of two three-run medians, not a paired-run ratio or a ratio of aggregate totals. Aggregating rounded report entries produced small errors: Luna's median is 7.6346116, which rounds to 7.63 rather than 7.64; GPT-5.5's mean is 4.9653254, which rounds to 4.97 rather than 4.96. The revision uses full-precision archived usage, reports medians and quartiles, and clarifies that provider input totals already include cached input. These ratios do not represent dollar costs.

7. **Moderate: history and job totals required coverage and attribution limits.** The 711 distinct histories, 5,042 distinct creating jobs and 552 error-state jobs reproduce after deduplication by server and native identifier. However, only 714/750 Galaxy run records have retrieved history contents; 32 have metadata only and four are unavailable. The source audits' analytical category also contains preprocessing and 102 legacy `upload1` jobs, while excluding `__DATA_FETCH__`. The 4,490 records not in error include 25 deleted and 11 paused jobs, so they cannot all be called successful. Current public snapshots can include inherited and later jobs. The revision reports all states and avoids treating the total as independent attempts or benchmark-attributed executions. The 93 recovery candidates across 49 runs remain candidates, not adjudicated scientific recoveries.

8. **Moderate: nominal verifier labels were liable to be mistaken for runtime scoring methods.** The original stratification used dataset labels such as `llm_verifier`. Archived evaluations instead include 599 `llm_verifier_auto_code`, 389 `range_verifier`, 286 `str_verifier_auto_numeric`, 209 `str_verifier`, 11 `str_verifier_rounded_numeric`, and six records without a mode. A nominal LLM label does not demonstrate that a language-model judge evaluated those runs. The revised Results remove that table; a future Methods section should document the actual evaluator transformations, tolerances and failure behavior.

## What the Data Establish

The available corpus supports a descriptive result: agents in the Galaxy condition frequently produced answers accepted by the original evaluator, with substantially higher provider-reported input-token use and inspectable execution records. It also supports exact coverage, recorded job-state and selected tool-label summaries. It does not establish causal improvements in accuracy, exclusive Galaxy execution across solved tasks, superior recovery, scientific method equivalence, human readability or economic value. Only BixBench-50 was examined; the analysis cannot supply performance estimates for GalaxyBench or BioAgent.

## Evidence Needed for Stronger Claims

- Provide the independent run inventory, task-selection procedure, model and harness versions, prompts, skills, budgets, stopping rules and replicate/seed policy. Explain the role of the superseded configuration and define the intended primary comparison.
- Reconcile the uniformly failed fresh-history check with the original traces. Attribute computation and final-answer derivation to Galaxy or external execution, and distinguish native tools from custom code executed inside Galaxy.
- Validate a representative set of scientific solutions and failures independently of final-answer acceptance. Resolve cases such as `bix-45-q1`, where error-free Galaxy jobs accompanied uniformly rejected answers, without assuming whether the method or evaluator was responsible.
- Define and adjudicate scientific methods, parameter changes and recovery episodes with a shared codebook across both conditions. Supply independent difficulty strata before making difficulty-dependent claims.
- For confirmatory accuracy claims, specify an appropriate estimand and dependence structure, including shared data across capsules. A non-inferiority claim additionally requires a scientifically justified margin; the exploratory bootstrap is not a substitute.
- Measure human review outcomes to support readability claims. Attribute tokens to operations and retries, and use documented provider accounting, cache categories, output usage, dated pricing and infrastructure costs for monetary comparisons.

These are scientific evidence requirements for the proposed claims, not a guarantee of editorial acceptance. Nature Methods describes its Analysis format as a comprehensive comparison of established methods and calls for strong validation in methodological Articles. Nature Portfolio also requires transparent reporting of experimental design and availability of the data, code and protocols needed to assess published claims. See the journal's [content types](https://www.nature.com/nmeth/content), [reporting standards](https://www.nature.com/nature-portfolio/editorial-policies/reporting-standards) and [reporting summary](https://www.nature.com/documents/nr-reporting-summary-flat.pdf).

## Reproducibility of This Review

The review read all 50 `analysis/<task>/history_analysis.md` files, all corresponding `history_analysis_evidence.json` files, and the archived original evaluator and usage records for all 1,500 runs. All markdown run scores and route labels agreed with the evidence records; all evidence scores and step checks agreed with their original evaluator artifacts; all input-token values agreed with original usage totals. No agent analysis was rerun and no score was changed. Capsule identifiers came from the allowed task metadata under `experiments/BixBench/`.

The [audit script](../scripts/audit_bixbench50_overview.py) writes [machine-readable results](bixBench50_overview_audit.json), including task summaries, configuration counts, coverage, source hashes and the bootstrap specification. Reproduce from the repository root with:

```sh
python3 scripts/audit_bixbench50_overview.py --output BixBench_50/bixBench50_overview_audit.json
```

The bootstrap samples 33 source capsules with replacement 100,000 times using seed 20260920. Each sampled capsule contributes all its questions and both conditions; the difference retains question weighting. The interval uses the 2.5th and 97.5th percentiles with linear interpolation. It quantifies sensitivity to resampling the observed capsules under an independence assumption, rather than validating the original selection protocol or eliminating confounding. Hashes document retained inputs; they do not independently authenticate remote source retrievals, whose limitations remain recorded in the source audits.
