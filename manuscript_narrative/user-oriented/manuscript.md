# Execution environments shape the reliability of biomedical AI agents

[Authors: author list, affiliations and corresponding author]

Analysis

## Abstract

AI agents now run computational biology analyses. However, users rarely know whether the agent's execution environment changes what they receive. We compared archived runs of four model configurations on 160 tasks from three benchmarks. Each task was run three times in an open-ended code environment and three times through Galaxy, a workbench of installed, versioned tools that records provenance. Observed accuracy was similar on BixBench-Verified-50 ({{bix_galaxy}}% versus {{bix_code}}%) and on CompBioBench graded against a reconstructed key ({{cb_galaxy}}% versus {{cb_code}}%). On workflow-derived IWC tasks, output agreement was higher through Galaxy ({{iwc_galaxy}} versus {{iwc_code}}) because fewer runs failed. Galaxy replicate sets had fewer discordant scored outcomes in all three benchmarks, but only the IWC interval excluded equality. Galaxy runs used a median {{tok_input_range}} times as many input tokens. Because prompts, budgets and run campaigns also differed between arms, these differences belong to the assigned arms, not to Galaxy alone.

## [Introduction]

AI agents built on large language models now plan analyses, write and run code, call bioinformatics tools and report biological conclusions with little human direction[@gao2024;@boiko2023;@bran2024;@biomni2026;@cellvoyager2026;@paper2agent2026]. A biologist who delegates an analysis to an agent needs to know three things: whether the result is right, whether a second run would give the same result and whether a reviewer could see how it was reached. Computational biology treats the last two as conditions for trusting a result[@sandve2013;@nekrutenko2012;@gruning2018cs;@heil2021]. However, benchmarks of these systems mostly ask the first question: whether a run reaches a reference answer[@bixbench2025;@compbiobench;@mlebench2024;@swebench2024]. Recent benchmarking studies have also shown that conclusions about computational methods depend on the endpoint, the reference and the baseline chosen[@luecken2022;@ahlmanneltze2025;@calibratedmetric2026;@saezrodriguez2026].

Agents usually execute in an open-ended code environment—an unrestricted shell in which the agent installs software and writes its own scripts. Two runs can install different versions, implement a statistic differently and preserve different execution artifacts. A scientific workbench offers an alternative. In Galaxy, analyses are composed from installed tool wrappers with pinned versions, and each step is recorded in an analysis history with its tool, version, parameters, inputs and outputs[@goecks2010;@galaxy2024;@toolshed2014]. Workbenches and workflow managers were built to make human analyses reproducible[@nekrutenko2012;@wratten2021]. However, comparative evidence about what they change for an agent user remains limited.

To address this gap, we analysed an archive in which the same model configurations performed the same tasks, three times each, in an open-ended code arm and in a Galaxy arm. This retrospective, paired analysis asks a user-facing question. Does the assigned execution arm change (1) benchmark accuracy, (2) the repeatability of scored outcomes across replicate runs, (3) the evidence left for review and (4) the cost of a run? Each benchmark keeps its own endpoint, and we report the design differences between arms beside every estimate. A companion manuscript analyses the same archive from the workbench side, covering interface failures, semantic fidelity, context use and agent-readiness requirements [Authors: companion manuscript citation]. The two papers share some descriptive measures, such as token use, but answer different questions with different primary endpoints.

## Results

### Comparing paired code and Galaxy arms with benchmark-specific endpoints

We analysed an archive of 4,240 runs (Fig. 1a,b). The primary population is {{n_primary_runs}} runs: four model configurations under the Codex agent harness (GPT-5.5, GPT-5.6 Sol, GPT-5.6 Luna and DeepSeek V4 Pro), 160 tasks, two arms and three replicate runs. The IWC endpoint uses the nine tasks scored in both arms, so the endpoint analyses use {{n_primary_runs_iwc_nine}} runs. We report {{n_superseded_runs}} BixBench-Verified-50 runs of DeepSeek V4 Pro under a superseded Claude Code harness separately, and we exclude {{n_astra_runs}} unpaired GPT-6 Astra runs. In the Galaxy arm, the agent reached usegalaxy.org (https://usegalaxy.org) through an interface built on the Model Context Protocol (https://modelcontextprotocol.io). It searched and inspected installed tools, ran them as Galaxy jobs and inspected its analysis history. On two benchmarks it could also submit user-defined tools—agent-written code that Galaxy runs as a job in a declared container. A local shell remained available for staging inputs and extracting answers.

We did not pool the benchmark-specific endpoints (Fig. 1c). First, BixBench-Verified-50 uses acceptance by the original evaluator[@bixbench2025]. Second, CompBioBench uses agreement with a reference key reconstructed from official leaderboard scores[@compbiobench]. The key, with 54 inferred and 46 predicted items, reproduces all 24 official paired replicate scores. Third, IWC uses output agreement (0–1) with the published Galaxy workflow output (https://github.com/galaxyproject/iwc).

The arms differed in more than the execution environment (Supplementary Table 1). First, Galaxy and code prompts were never identical ({{prompt_pairs_identical}} task–configuration–replicate pairs). Galaxy prompts added execution policy and were longer: median {{prompt_words_BixBench50}} words on BixBench-Verified-50 and {{prompt_words_CompBio}} on CompBioBench. Second, CompBioBench code prompts stated a 120-minute limit, whereas Galaxy prompts stated none. IWC runs had a 6- or 12-hour limit that depended on start time, and the two arms had equal limits in {{iwc_budget_matched}} replicate pairs. Third, CompBioBench Galaxy runs executed in a container, whereas code runs executed in a host conda environment. Fourth, {{cb_outcome_named_runs}} CompBioBench Galaxy runs, and no code runs, came from run campaigns whose names refer to wrong answers or target scores. Extended Data Fig. 1 gives each user-facing measure as a Galaxy ÷ code ratio. Every estimate below is therefore a difference between assigned arms that includes all of these differences, not an effect of Galaxy alone.

### Observed benchmark accuracy is similar in the two arms

We first compared benchmark accuracy. On BixBench-Verified-50, {{bix_galaxy}}% of Galaxy runs and {{bix_code}}% of code runs were accepted, a difference of {{bix_diff}} percentage points (95% confidence interval {{bix_diff_ci}}; Fig. 2a). The four configurations differed by {{bix_cfg_diff_range}} points, and most tasks had similar numbers of correct runs in both arms (Extended Data Fig. 2a). After removing {{bix_sens_bench_side_n}} tasks flagged by the audit for reference, grading or answer-exposure problems, the difference was {{bix_sens_bench_side_diff}}. One such task, bix-30-q3, illustrates both problems. Its reference holds only when raw values are analysed, and code runs that reproduced the source paper's normalization reached a defensible alternative answer. In addition, all three DeepSeek V4 Pro Galaxy runs on this task read the benchmark row containing the reference answer before answering. Under the superseded harness, accuracy was {{bix_superseded_galaxy}}% versus {{bix_superseded_code}}%, a difference of {{bix_superseded_diff}} points. Because that harness differed from the primary one in more than its environment, we do not generalize from it.

On CompBioBench, {{cb_galaxy}}% of Galaxy runs and {{cb_code}}% of code runs agreed with the reconstructed key ({{cb_diff}}; {{cb_diff_ci}}; Fig. 2b). The difference was similar in three sensitivity analyses: scoring one task against an alternative key, {{cb_sens_alt_genome_D}}; removing the two audited tasks with predicted keys, {{cb_sens_no_predicted}}; and keeping only the 53 tasks with any run that deviated from the key, {{cb_sens_informative}}. In contrast, removing the {{cb_outcome_named_cells}} task–configuration cells that contained a run from an outcome-named campaign reversed its sign, to {{cb_sens_no_outcome_campaigns}}.

On the nine IWC tasks, mean output agreement was {{iwc_galaxy}} in the Galaxy arm and {{iwc_code}} in the code arm ({{iwc_diff}}; {{iwc_diff_ci}}; Fig. 2c). Leaving out one task at a time gave {{iwc_loto}}. The difference came from a few failed runs (Fig. 2d): without the {{iwc_zero_tasks_n}} tasks that contained a zero-scored run, it was {{iwc_sens_no_zero}}. Two further checks qualify the score. First, the ATAC-seq route references were calibrated from agent runs for {{iwc_atac_agent_calibrated_code}} of 12 code and {{iwc_atac_agent_calibrated_galaxy}} of 12 Galaxy runs, so that task partly scores runs against themselves; removing it gave {{iwc_sens_no_atac}}. Second, restricting to the {{iwc_budget_matched_pairs_nine}} replicate pairs with equal time limits gave {{iwc_sens_budget_matched}}. The headline score also omits components that matter biologically (Fig. 2e). For example, the RNA-seq composite does not include the set of significant genes: a Galaxy run that reported {{iwc_rnaseq_edger_genes}} significant genes, against {{iwc_rnaseq_ref_genes}} in the reference, scored {{iwc_rnaseq_edger_score}}. Together, these results show that observed accuracy was similar in the two arms and that the IWC difference came from a few failed runs.

### Galaxy replicate sets have fewer discordant scored outcomes

A user who runs an analysis once needs that run to be representative. We called a replicate set discordant when one or two of its three runs were scored correct or, for IWC, when its three scores spanned more than 0.05. Galaxy sets were discordant less often in every benchmark (Fig. 3a–c): {{bix_disc_galaxy}} versus {{bix_disc_code}} on BixBench-Verified-50, a ratio of {{bix_disc_ratio}}; {{cb_disc_galaxy}} versus {{cb_disc_code}} on CompBioBench, {{cb_disc_ratio}}; and {{iwc_disc_galaxy}} versus {{iwc_disc_code}} on IWC, {{iwc_disc_ratio}}. Only the IWC interval excluded equality. Paired transitions ran in both directions. Of 200 BixBench-Verified-50 task–configuration pairs, {{bix_trans_better}} had a better set outcome in Galaxy and {{bix_trans_worse}} a worse one; on CompBioBench the counts were {{cb_trans_better}} and {{cb_trans_worse}} of 400 (Fig. 3a).

The share of tasks solved by all three runs was higher in Galaxy for {{unan_pairs_positive}} configuration–benchmark pairs, by {{unan_range}} points. Pooled, it was {{bix_unan_galaxy}}% versus {{bix_unan_code}}% on BixBench-Verified-50, a difference of {{bix_unan_diff}} points, and {{cb_unan_galaxy}}% versus {{cb_unan_code}}% on CompBioBench, {{cb_unan_diff}} points (Fig. 3d). In contrast, normalized answer agreement showed no consistent Galaxy advantage, and replicate pairs matched at similar rates ({{bix_answer_agree}} on BixBench-Verified-50 and {{cb_answer_agree}} on CompBioBench, Galaxy first; Extended Data Fig. 2b). These results show that Galaxy replicate sets more often agreed on the scored outcome, but not more often on the normalized answer.

### Implementation and version differences underlie divergent and stable results

To see why replicate runs diverged, we compared each scored-incorrect run in a discordant BixBench-Verified-50 set with its scored-correct siblings (Fig. 4a). In the code arm, {{div_codex_hw_code}} such runs differed by a hand-written method or a different software version, against {{div_codex_hw_galaxy}} in Galaxy. Galaxy divergences more often arose from final-step errors, from no answer and from interface traps ({{div_codex_trap_galaxy}}), a mechanism the code arm cannot have. The superseded harness showed the same contrast ({{div_sup_hw_code}} versus {{div_sup_hw_galaxy}}).

Individual tasks show how a fixed implementation can make a result stable, whether right or wrong (Fig. 4b–d). On bix-55-q1, two code runs installed BUSCO 5.7.1[@busco2021] instead of reading the supplied BUSCO 5.8.0 outputs and reported 100 complete genes; all 12 Galaxy runs reported the reference, 101. On bix-45-q1, all 12 Galaxy runs and four code runs returned 1.52 × 10^−56^. Ten of these Galaxy runs used the wrapper and two used user-defined tools; across all five configurations the counts were 13 and 2. This is the value under the current PhyKIT definition[@phykit2021] and is scientifically defensible. The reference instead encodes the definition of PhyKIT 2.0.3, which eight code runs reproduced, mostly by dating the input files. The wrapper did not show which PhyKIT version it ran. On encode-atac-pipeline-q1, two Galaxy runs executed the ENCODE ATAC-seq pipeline (https://github.com/ENCODE-DCC/atac-seq-pipeline) in its official container as a Galaxy job and reproduced the reference. Eleven code runs executed it outside the container and reported nearby values; host-library differences are an untested explanation. Seven Galaxy runs computed untrimmed outputs after staging removed file extensions, and another copied an untrimmed answer from a pilot history after its own jobs failed.

On IWC, five of 117 scored code runs and three of 120 Galaxy runs scored below 0.5 (Fig. 4e). Two code-run mechanisms did not occur in Galaxy runs: a hand-written multiple-testing correction[@bh1995] and sample identifiers lowercased from folder names. Submitting the wrong contig as a mitochondrial genome occurred in both arms, and two Galaxy runs were scored against a route other than the one they followed. Together, these cases are consistent with installed tools reducing implementation variance.

### Each arm leaves different evidence for review

Execution traces were retrieved for {{trace_code_primary}} code runs and {{trace_galaxy_primary}} Galaxy runs in the primary population (Fig. 5a). Only Galaxy runs also had analysis histories recording tools, parameters and job states: {{hist_primary}} primary runs and {{hist_all}} of all Galaxy runs. Execution errors per run were similar in the two arms on BixBench-Verified-50, higher in Galaxy on CompBioBench and lower on IWC, and they differed in type (Extended Data Fig. 3). The interface compared requested with resolved non-dataset parameters in {{check_coverage_primary}} tool-run calls. The remaining calls lack a recorded comparison, so success alone cannot certify their parameter fidelity.

We then used a targeted, AI-assisted trace audit to review tasks with wrong, scored-incorrect or low-scoring runs and one near-perfect IWC workflow with changed significant genes ({{audit_cases}} cases; Fig. 5b). The primary cause was an agent analysis error in {{audit_C5}} cases and a reference that depends on an unstated choice in {{audit_C3}}. The Galaxy platform, a wrapper or the server accounted for {{audit_C4}}, an equivalent answer in another notation for {{audit_C1}}, a scoring artifact for {{audit_C2}} and another cause for {{audit_C6plus}}.

The arm label records the assignment, not where computation ran (Fig. 5c). An unvalidated screen found shell commands naming an analysis program in {{screen_BixBench50}}, {{screen_CompBio}} and {{screen_IWC}} of Galaxy runs on the three benchmarks. The audit confirmed four kinds of departure. First, {{local_answers}} CompBioBench Galaxy answers were computed in the local shell after user-defined-tool execution became unavailable ({{local_answers_correct}} scored correct). Second, {{cross_run}} answers were copied across runs through the shared Galaxy account. Third, Galaxy-arm agents sometimes called the Galaxy API directly from the shell, bypassing the interface's checks; the companion study quantifies this. Fourth, in {{retrieval_tasks}} task cases, agents in either arm retrieved or tried to retrieve benchmark answers online. These results show that provenance records let a reviewer see what ran, including departures from the assigned arm.

### Resource use, majority voting and Galaxy-specific failures

Within the same task and configuration, Galaxy runs used a median {{bix_tok_input_tokens}}, {{cb_tok_input_tokens}} and {{iwc_tok_input_tokens}} times the input tokens of code runs on the three benchmarks (Fig. 6a). These ratios cover the cells with token records in both arms: {{bix_tok_cells}}, {{cb_tok_cells}} and {{iwc_tok_cells}}. Most of the excess was cached context re-read on each turn. Uncached input rose {{bix_tok_uncached}}, {{cb_tok_uncached}} and {{iwc_tok_uncached}} fold, and output tokens {{bix_tok_output_tokens}}, {{cb_tok_output_tokens}} and {{iwc_tok_output_tokens}} fold.

A user can also run an agent three times and take the majority answer. We applied outcome-blind voting rules retrospectively (Methods). Under rule A, which compares numbers to ten significant digits, voting changed BixBench-Verified-50 accuracy from {{bix_code_single}}% to {{bix_code_vote}}% in the code arm and from {{bix_gal_single}}% to {{bix_gal_vote}}% in Galaxy. On CompBioBench it changed accuracy from {{cb_code_single}}% to {{cb_code_vote}}% and from {{cb_gal_single}}% to {{cb_gal_vote}}% (Fig. 6b). Under rule B, which compares numbers to three significant digits, BixBench-Verified-50 voting reached {{bix_code_vote_B}}% in code and {{bix_gal_vote_B}}% in Galaxy (Extended Data Fig. 4). Three code runs used a median {{bix_code_three_tok}} and {{cb_code_three_tok}} million input tokens, fewer than one Galaxy run ({{bix_gal_one_tok}} and {{cb_gal_one_tok}} million). These results show that whether code voting matches one Galaxy run depends on the benchmark and matching rule. Code runs retain their transcripts; voting adds no workflow provenance.

Galaxy runs also took {{bix_actions_range}} and {{cb_actions_range}} times as many actions as code runs on BixBench-Verified-50 and CompBioBench (Holm-adjusted P < 0.05 for {{bix_actions_sig}} and {{cb_actions_sig}} configurations) and {{iwc_actions_range}} times as many on IWC ({{iwc_actions_sig}}; Fig. 6c). The audit attributed {{galaxy_specific_runs}} scored-incorrect Galaxy runs, across all five configurations, to {{galaxy_specific_mechanisms}} Galaxy-specific mechanisms (Fig. 6d), and four of them raised no job error. They include the undisplayed PhyKIT version on bix-45-q1, whose 15 Galaxy answers are scientifically defensible but were scored incorrect. Together, these results show that Galaxy runs used more tokens and actions at the median and had failure mechanisms of their own.

## Discussion

Users of AI agents need results that are accurate, repeatable and open to review. For a user choosing between an agent that writes its own code and one that works through Galaxy, this archive shows similar observed benchmark accuracy and more replicate sets with consistent scored outcomes through Galaxy. Galaxy runs also kept analysis histories, at several times the token cost; these histories enabled attribution of scientific errors, version dependencies and departures from the assigned arm but do not by themselves reproduce a result. The small accuracy differences were sensitive to how the reference was built and which runs were included, and changed sign without the outcome-named CompBioBench campaigns or the BixBench-Verified-50 tasks flagged for reference, grading or answer-exposure problems. The repeatability difference had the same direction in all three benchmarks and in most configurations, but its interval excluded equality only for IWC. Because prompts, budgets, runtime environments and run campaigns differed between arms, these are differences between assigned arms that we cannot assign to Galaxy alone.

The case analyses suggest one mechanism that a user can act on: installed tools constrain implementation choices, although matching tool names alone does not ensure matching parameters or outputs. Most code-arm divergence on BixBench-Verified-50 came from re-implementing a method or installing a different version. The mechanism cuts both ways. On bix-45-q1, every Galaxy run returned the current PhyKIT definition. That answer is scientifically defensible but was scored incorrect because the reference used a retired version, and the wrapper did not show which version it ran. A stable answer is useful only when the user can confirm that the pinned version is the intended one.

This study has several limitations. First, it is retrospective. Replicate labels are not matched random seeds, the four configurations represent a period in which models changed quickly, and equivalence and non-inferiority remain untested. Second, CompBioBench grades depend on a private key, nearly half of which was predicted rather than inferred and which lacks independent scientific adjudication and validation against an official item key. The IWC headline score measures agreement with a reference route, not scientific validity, and includes circular ATAC-seq references. Third, repeatability, reproducibility and provenance are different properties. We measured repeatability within an arm and configuration and the coverage of execution records, but did not test reproducibility by another team or on another deployment. We replayed no history, re-executed no analysis and asked no domain expert to judge scientific validity blind to the arm. Fourth, the case analyses come from a small number of tasks and do not test whether installed tools reduce implementation variance. Fifth, the AI-assisted trace audit was targeted rather than exhaustive and did not split causes by arm. Its counts of local computation, copying and answer retrieval are observed cases, not prevalence, and the unvalidated execution-location screen may give false positives or miss computation. Sixth, all Galaxy runs used one public server, one interface and one shared account, which allowed answers to be copied between runs. Finally, agents in both arms sometimes retrieved benchmark answers online, so all three benchmarks may be partly contaminated[@kapoor2023].

Future work should test these findings prospectively with the protocol in Supplementary Note 1, which specifies matched prompts and budgets, fixed campaigns, blinded expert review, independent replay of Galaxy histories and code transcripts, and a second Galaxy deployment. Replay and review-time measurements are also needed to determine the value of Galaxy records to users.

## Methods

### Archive and analysed populations

We analysed an archive of 4,240 agent runs on 160 tasks: BixBench-Verified-50 (50 questions from 33 source capsules; 1,500 runs)[@bixbench2025], CompBioBench (100 tasks; 2,500 runs)[@compbiobench] and IWC (10 tasks derived from published Galaxy workflows; 240 runs). The archive preserves execution traces, submitted answers or outputs, evaluator records and retrieved Galaxy analysis histories where available. No agent code was re-run, no Galaxy job was submitted and no file in the repository's ground-truth directory was opened for this analysis. Supplementary Table 2 lists the analysed population, the eligible units and the numerator and denominator for every measure.

The primary population comprises four model configurations under the Codex agent harness: GPT-5.5, GPT-5.6 Sol, GPT-5.6 Luna (maximum reasoning effort; the others, high) and DeepSeek V4 Pro. Configuration names are archive labels; exact runtime model snapshots and interface commits are incompletely recorded. Each configuration ran every task three times per arm. DeepSeek V4 Pro also ran BixBench-Verified-50 under a superseded Claude Code harness; these 300 runs are reported separately. GPT-6 Astra ran CompBioBench once per task in the code arm only and enters no comparison.

### Execution arms and recorded design differences

In the open-ended code arm, the agent worked in a shell and could install and run any software. In the Galaxy arm, the agent reached usegalaxy.org through an interface implemented as a Model Context Protocol server. The interface exposed tool search, tool inspection, history and dataset inspection, job submission and waiting and, on BixBench-Verified-50 and CompBioBench, user-defined tools. Before submitting a job, the interface validated the request; after the job, it compared the requested non-dataset parameters with those Galaxy resolved. Galaxy-arm prompts required evidence-bearing computation to run in Galaxy and reserved the local shell for staging and answer extraction.

Design differences between arms were extracted read-only from the archive. We recorded prompt hashes and lengths, time limits, harness and container labels, runtime model identifiers, run dates, exposed tools and run campaigns (Supplementary Table 1; `derived/design/` in the code release). For each CompBioBench run, its campaign was taken from its archived workspace path and checked against the official score-vector registry. Campaigns whose names refer to wrong answers or target scores (`wrong19`, `wrongset`, `fastwrong`, `target84`, `near84`) are called outcome-named.

### Endpoints and grading

BixBench-Verified-50 runs keep their original binary evaluator decisions; no run was regraded. CompBioBench archives no per-run grades. We graded each run as correct when its submitted answer, after removing leading and trailing white space, exactly matched the reconstructed key. One label substitution was applied before matching: the text "Proximal enhancer,EH38E1957012" was replaced with "pELS,EH38E1957012". No case, spacing or numeric normalization was applied in grading; those rules apply only to the answer grouping described below. The key comes from the lab results repository `goeckslab/galaxy-agent-benchmark` (private; commit `bdc00429f559`). Answers for 54 items were inferred from official leaderboard scores (file SHA-256 prefix `959dd3f2`), and answers for 46 items were predicted (`57a6a92d`). Official scores (`055cfb18`) were used for verification. The grading script checks each file against its SHA-256 and stops unless the grades reproduce all 24 official paired replicate scores. Two archived replicate scores used in earlier summaries are one point lower than our grades. The key files are kept outside the repository because agents run from it, so CompBioBench grades cannot be regenerated without access to the private key; Source Data give grades and replicate outcomes but no answers. IWC uses the archived output agreement score (0–1), which is task-specific and defined against the published workflow output. Condition comparisons use the nine tasks scored in both arms. The host-read-removal task was excluded because three code runs followed unsupported routes and two Galaxy runs had conflicting scores.

### Sensitivity analyses

These sensitivity analyses are retrospective and exploratory; they were not preregistered. For BixBench-Verified-50, we excluded 15 tasks coded C1, C2, C3 or C6: equivalent answers, scoring artifacts, underspecified references or reference/answer-exposure problems. For CompBioBench, we made four changes: we scored genome-coords-q1 against an alternative key D; excluded the two audited tasks with predicted keys; kept only the 53 tasks with any run that deviated from the key; and excluded every task–configuration cell containing a run from an outcome-named campaign. For IWC, we excluded the ATAC-seq task, whose route references were calibrated from agent runs, as recorded in each run's evaluation record. We also excluded the tasks containing a zero-scored run, restricted the comparison to replicate pairs with equal time limits and left out one task at a time. IWC components (Fig. 2e) were read from each run's evaluation record.

### Replicate sets, repeatability and answer agreement

A replicate set is the three replicate runs of one task, model configuration and arm. For binary endpoints, a set is all correct, discordant (one or two correct) or none correct. For IWC, a set is discordant when its three output-agreement values span more than 0.05; nine-task counts are primary, and Supplementary Table 2 gives all-ten-task counts ({{iwc_disc_ten}}). Unanimous accuracy is the share of tasks with an all-correct set. Answer agreement is the share of the three replicate-run pairs in a set whose answers match: decimal numbers within a relative 10^−4^, integers exactly and other text after removing case and spaces.

### Outcome-blind majority vote

Answers were grouped without grades: surrounding white space, case and spaces were normalized. Rule A compared numbers to ten significant digits; rule B used three. Percentage units remained distinct. A group of at least two selected its earliest-replicate answer; no consensus counted as incorrect. We reused that representative's archived grade rather than regrading. Selection is independent of outcomes, but this surrogate depends on the original grading; groups with inconsistent member grades are flagged in Source Data. The share of sets with at least two correct runs is an oracle shown only for comparison.

### Divergence mechanisms, targeted audit and execution location

For each scored-incorrect run in a discordant BixBench-Verified-50 set, we compared its trace with those of its scored-correct siblings. The decisive difference was assigned to one mechanism: a hand-written method or a different software version, a domain convention, a final-step error, a Galaxy interface trap, or no answer or benchmark source files read. The targeted audit reviewed the traces of every task with at least one wrong, scored-incorrect or low-scoring run, plus one IWC workflow whose near-perfect score concealed a changed significant-gene set (93 task cases). Each case received one primary cause and cross-cutting flags for local computation, cross-run reuse and answer retrieval (`individual_error_analysis.md`, with trace line references). The audit and the divergence comparisons were performed with an AI assistant, and every assignment cites trace lines that a reader can check [Authors: describe the human review of the AI-assisted audit, including who reviewed which cases and how disagreements were resolved]. The execution-location screen flagged Galaxy-arm runs whose shell commands named an analysis program. This screen is unvalidated and can miss local computation or flag staging commands.

### Execution errors, tokens and actions

An execution error is a shell command with a non-zero exit code, excluding exit code 1 with no message (such as a search with no match), or a Galaxy job in the error state. Error types come from one ordered set of rules applied to shell output and Galaxy job messages (Extended Data Fig. 3). An error is counted as occurring in a run that ended correct when its run was scored correct; we do not interpret this as repair of the error. Input tokens include cached input; uncached input is input minus cached input. An action is one agent tool call. Token and action ratios are medians, over task × model configuration cells with records in both arms, of the ratio of the Galaxy to the code median.

### Statistics

Intervals are 95% percentile cluster-bootstrap intervals with 20,000 resamples[@davison1997]. Resampling units are source capsules for BixBench-Verified-50 and tasks for CompBioBench and IWC, which preserves the pairing of arms within a cluster. Intervals taken from the archived analyses (BixBench-Verified-50 and IWC accuracy differences) used seed 20260922, and new intervals used seed 20261002. Action comparisons used two-sided Wilcoxon signed-rank tests on per-task medians with Holm adjustment[@holm1979]. All intervals are pointwise and exploratory; we make no equivalence, non-inferiority or causal claim. Values are rounded half away from zero.
