# Benchmarking biomedical agent reliability in Galaxy and open-ended code

[Authors: author list, affiliations and corresponding author]

## Abstract

Biomedical agents can produce plausible answers without checking whether their analyses support them. We analysed 3,840 assigned runs in which four model configurations attempted each task of three benchmarks three times, in Galaxy and in open-ended code. Benchmark performance was similar between the two environments, and Galaxy solved more tasks in all three attempts, although per-model intervals were wide. An audit of every task with a rejected answer attributed most failures to agent analyses that lacked adequate verification and about a third to benchmark references or scoring; domain knowledge alone and Galaxy platform faults were uncommon. Galaxy used {{cb_total_ratio_point}}–{{bix_total_ratio_point}} times more total input tokens than open-ended code on two question-answering benchmarks, but not on workflow tasks. Interface traces located this overhead in tool discovery, schema errors and failures returned without diagnostics. A planned intervention study will test interface changes that target these costs; its results are pending.

## [Introduction]

Biomedical agents increasingly connect language models to analysis software, literature and datasets. Systems such as Biomni, Paper2Agent and CellVoyager illustrate the potential of tool-assisted investigation, while computational biology benchmarks make task performance measurable.[@biomni2026;@paper2agent2026;@cellvoyager2026;@bixbench2025;@compbiobench] A submitted answer nevertheless compresses many decisions: which inputs were used, whether the chosen method addressed the question, how execution failures were handled and whether an apparently successful result was checked. Distinguishing useful automation from plausible but unsupported conclusions requires evaluating these decisions as well as the answer.

Galaxy provides a workbench in which analyses retain histories, datasets, tool versions and job records.[@galaxy2024;@goecks2010] These records could make agent behaviour easier to inspect, but interacting with a workbench may also increase context and execution overhead. Workflow reproducibility and machine-learning evaluation standards therefore motivate measuring answer performance, analysis decisions and resource use separately.[@wratten2021;@heil2021] Critical benchmarking can show where added complexity delivers value and where simpler alternatives suffice.[@ahlmanneltze2025]

Here we compare Galaxy with open-ended code as execution environments for biomedical agents across three benchmarks. We find that agents performed similarly in both environments; that when they failed, the recorded analyses most often lacked adequate verification rather than biological or Galaxy knowledge; and that Galaxy's input-token overhead was concentrated in specific interface interactions that can be redesigned. We close by specifying how benchmark measurements can drive and test such interface changes.

## Results

### 1. A paired benchmark of biomedical agents in Galaxy and open-ended code

The archive contains 4,240 runs spanning BixBench-Verified-50, CompBioBench and ten workflows from the Galaxy Intergalactic Workflow Commission (IWC). Primary comparisons use four shared Codex configurations—GPT-5.5, GPT-5.6 Sol, GPT-5.6 Luna and DeepSeek V4 Pro—each attempting every task three times in each environment, for 3,840 assigned runs (Fig. 1). We exclude 100 code-only Astra runs, which have no Galaxy counterpart, and 300 runs from a superseded harness. One IWC task lacks comparable scores between arms, leaving 3,816 runs for endpoint analyses; all 160 tasks remain in the interface analyses.

Each benchmark keeps its own endpoint. BixBench uses the original evaluator's binary acceptance. CompBioBench uses agreement with a reconstructed answer key, in which 54 references were inferred from recorded scores and 46 from predicted answers. IWC uses continuous agreement (0–1) with curated workflow outputs on nine tasks. Tokens are the recorded model input, including cached context that the model rereads.

The two arms differ by design. Galaxy prompts add execution policy, including history use, permitted tools, rules for user-defined tools (UDTs) and interface timeouts. They were longer on BixBench ({{bix_prompt_words_galaxy}} versus {{bix_prompt_words_code}} median words) and CompBioBench ({{cb_prompt_words_galaxy}} versus {{cb_prompt_words_code}}) but not on IWC ({{iwc_prompt_words_galaxy}} versus {{iwc_prompt_words_code}}). Time budgets, runtime environments and campaign histories also differ (Methods). We therefore compare the assigned arms as deployed—agent plus execution environment—rather than estimating an effect of Galaxy alone.

### 2. Agents perform similarly in Galaxy and open-ended code

Overall performance was similar between environments (Fig. 2). On BixBench-Verified-50, acceptance was {{bix_code}}% with open-ended code and {{bix_galaxy}}% with Galaxy, a difference of {{bix_diff}} percentage points (estimate and 95% cluster-bootstrap interval; Fig. 2a). CompBioBench agreement was {{cb_code}}% and {{cb_galaxy}}%, a difference of {{cb_diff}} points (Fig. 2b). Both differences remained within about one point of zero after removing 15 BixBench tasks with audited benchmark-side problems ({{sens_BixBench_exclude_benchmark_side_C1_C2_C3_C6}}) or 66 CompBioBench task–configuration cells containing Galaxy runs from campaigns named for wrong answers or target scores ({{sens_CompBio_exclude_outcome_named_cells}}; Fig. 2d,e). IWC agreement was {{iwc_code}} with code and {{iwc_galaxy}} with Galaxy ({{iwc_diff}}; Fig. 2c); three tasks containing a zero-scored run account for most of that difference ({{sens_IWC_exclude_tasks_with_zero_run}} without them; Fig. 2f).

The best configuration depended on the benchmark. GPT-5.5 had the highest BixBench acceptance in both arms ({{bix_best_galaxy}}% in Galaxy), Sol the highest CompBioBench agreement in both arms ({{cb_best_galaxy}}% in Galaxy), and Sol and DeepSeek V4 Pro the highest IWC agreement with code ({{iwc_best_open_ended_code}}) and Galaxy ({{iwc_best_galaxy}}), respectively (Fig. 2a–c). Differences among the leading configurations were small relative to their intervals, so these are rank changes rather than a demonstrated model-by-benchmark interaction. They argue for evaluating a configuration on the intended workload rather than assuming that one model fits all.

Galaxy reached the correct answer more consistently. The share of binary task–configuration sets with all three attempts accepted rose from {{bix_three_code}}% to {{bix_three_galaxy}}% on BixBench and from {{cb_three_code}}% to {{cb_three_galaxy}}% on CompBioBench. The point estimate favoured Galaxy for every configuration on both benchmarks, although each configuration's interval included or touched zero (Fig. 3a,b). The gain came from fewer mixed-outcome sets—{{bix_mixed_sets_code}} versus {{bix_mixed_sets_galaxy}} on BixBench and {{cb_mixed_sets_code}} versus {{cb_mixed_sets_galaxy}} on CompBioBench—not from fewer persistent failures. Of the {{bix_three_rejected_sets_code}} code and {{bix_three_rejected_sets_galaxy}} Galaxy BixBench sets rejected in all three attempts, {{bix_three_rejected_sets_both}} were the same task and configuration in both arms; on CompBioBench, {{cb_three_rejected_sets_both}} of {{cb_three_rejected_sets_code}} coincided (Fig. 4d). Pooled Galaxy/code ratios of discordant sets were {{BixBench50_discordance_ratio}}, {{CompBio_discordance_ratio}} and {{IWC_discordance_ratio}} for BixBench, CompBioBench and IWC (Fig. 3c), but discordance rose for DeepSeek on BixBench and for Sol on CompBioBench.

Galaxy runs combined installed tools with agent-written code. Agents created UDTs—their own scripts, executed as Galaxy jobs in a container—in {{bix_udt_attempt}} of 600 BixBench and {{cb_udt_attempt}} of 1,200 CompBioBench Galaxy runs, and at least one UDT job completed in {{bix_udt_jobok}} and {{cb_udt_jobok}} of these runs (Fig. 3d,e). Use varied by configuration, from under 10% of DeepSeek BixBench runs to nearly 90% of GPT-5.5 CompBioBench runs. Runs with a completed UDT job were accepted at {{bix_udt_ok_acc}}% on BixBench, against {{bix_no_udt_acc}}% for runs without UDTs, and at {{cb_udt_ok_acc}}% on CompBioBench. The {{cb_udt_nook_runs}} CompBioBench runs whose UDT jobs never completed were accepted at {{cb_udt_nook_acc}}%. Agents chose when to write UDTs, so these are associations rather than effects. The IWC interface did not expose UDTs.

### 3. Failures reflect insufficient verification more than missing knowledge

To ask why agents failed, we audited every task on which at least one run was rejected: {{census_bix}} BixBench and {{census_cb}} CompBioBench tasks among the primary configurations, together with seven IWC workflows and tasks that failed only in other archived configurations ({{audit_cases}} tasks in total; Methods). Each task received one primary cause and non-exclusive tags from an AI-assisted review of its traces and outputs. Among the {{census_tasks}} failing binary-benchmark tasks, the primary cause was agent analysis in {{census_agent}} ({{census_agent_pct}}%), the benchmark's reference, scoring or answer provenance in {{census_benchmark}} ({{census_benchmark_pct}}%) and Galaxy platform or wrapper behaviour in {{census_galaxy}} ({{census_galaxy_pct}}%; Fig. 4a). Benchmark-side causes dominated BixBench ({{census_bix_benchmark}} of {{census_bix}} tasks) and, because they tended to fail every attempt, accounted for {{census_benchmark_runs_pct}}% of all rejected primary runs.

Insufficient verification was the most common feature of agent failures. It was tagged in {{census_verification}} of the {{census_tasks}} failing tasks ({{census_verification_pct}}%) and in {{census_c5_verification}} of {{census_c5}} agent-analysis tasks ({{census_c5_verification_pct}}%; Fig. 4b). Domain knowledge was implicated in {{census_domain}} tasks, {{census_both}} of them together with insufficient verification; domain knowledge alone accounted for {{census_domain_only}} ({{census_domain_only_pct}}%). The recorded failures therefore point less to missing biological or Galaxy knowledge than to analyses that were not checked before an answer was submitted.

Replicates separate two kinds of failure. A task–configuration set with one or two rejected attempts shows that the same agent can succeed or fail on the same task, depending on the analysis path it takes; a set with all three rejected shows a failure that repeats. Persistent failures recurred across arms (Fig. 4d) and were enriched for benchmark-side causes: {{persistent_benchmark}} of the {{persistent_tasks}} tasks with a set rejected three times had a reference, scoring or provenance cause, compared with {{sporadic_benchmark}} of {{sporadic_tasks}} tasks whose failures were sporadic (Fig. 4c). Sporadic failures were mostly agent analysis ({{sporadic_agent}} of {{sporadic_tasks}}) and included {{sporadic_galaxy}} of the {{census_galaxy}} Galaxy platform tasks, which other attempts overcame. Insufficient verification occurred in both groups ({{persistent_verification}} of {{persistent_tasks}} and {{sporadic_verification}} of {{sporadic_tasks}}). Three failures in three attempts thus often signal an ambiguous task, reference or scorer, or a consistent analysis mistake, whereas one or two failures point to divergent analysis paths that sibling traces can compare.

Traces show which checks were missing (Fig. 4e). For bix-52-q2, a digits-only chromosome filter silently dropped W and Z, and the run accepted the reduced denominator; another run asserted the expected 20 groups and avoided the error. In variant-status-q1, apparent alternate alleles came from read ends; two Sol Galaxy runs audited allele support by read position and rejected the artifact. In exogenous-mix-reads-q1, code and Galaxy runs fitted and scored a classifier on the same reference reads, whereas a correct run held out read groups. Checks were also run and then ignored: on histone-chip-q1, a DeepSeek Galaxy run retained a candidate after its own overlap check returned near-zero agreement, and on the IWC mitogenome task, circularity and self-mapping were taken as evidence of organellar identity. The same mistakes occurred in both arms. Galaxy histories retained the tools, parameters and job states behind each decision, which located where each analysis went wrong; successful execution, however, did not establish that the analysis was appropriate.

### 4. Galaxy's token overhead is concentrated in addressable interface costs

Galaxy used more input tokens than open-ended code on the two question-answering benchmarks but not on the workflow benchmark. Total Galaxy input divided by total code input over paired task–configuration cells was {{bix_total_ratio}} on BixBench and {{cb_total_ratio}} on CompBioBench, but {{iwc_total_ratio}} on IWC (Fig. 5g). On IWC, some code runs consumed very large inputs—a mean of {{iwc_atac_code_mean}} million tokens per code run on ATAC-seq, against {{iwc_atac_galaxy_mean}} million in Galaxy—and Galaxy used less total input for three of four configurations. Excluding cached context, Galaxy's point estimate exceeded code in all {{uncached_ratio_cells_above_one}} benchmark–configuration comparisons (pooled uncached ratios {{bix_total_uncached}}, {{cb_total_uncached}} and {{iwc_total_uncached}}). The median of within-cell ratios, which weights each task equally, gave higher estimates ({{bix_tokens_total}}, {{cb_tokens_total}} and {{iwc_tokens_total}}). Within discordant sets, rejected and accepted attempts used similar input (Fig. 5h); we found no consistent token difference between correct and incorrect answers in either arm.

Model choice changed resource use as much as the environment did. On tasks with complete records in all eight model–arm groups, GPT-5.5 lay on the point-estimate accuracy–token frontier in {{frontier_5.5}} of six benchmark–arm views and Sol in {{frontier_sol}} (Fig. 5a–f). Sol had the highest CompBioBench agreement in both arms and the highest IWC agreement with code, at higher input than GPT-5.5. Luna was dominated in every view and DeepSeek V4 Pro in five, using more input without higher accuracy. The Galaxy/code ratio also varied by configuration, from {{bix_5.5_total}} for GPT-5.5 to {{bix_luna_total}} for Luna on BixBench (Fig. 5g). Selecting an efficient configuration is therefore a first-order lever on resource use in either environment.

Interface traces show where Galaxy's additional context came from. The primary configurations made {{primary_interface_calls}} Galaxy interface calls, and the input of each Galaxy run tracked its number of interface calls and shell commands closely (Spearman ρ = {{bix_actions_rho}}, {{cb_actions_rho}} and {{iwc_actions_rho}} for BixBench, CompBioBench and IWC), so fewer interactions should mean fewer tokens. Tool discovery was the largest burden: search and tool inspection made up {{bix_discovery_calls}}%, {{cb_discovery_calls}}% and {{iwc_discovery_calls}}% of calls and {{bix_discovery_chars}}%, {{cb_discovery_chars}}% and {{iwc_discovery_chars}}% of returned text (Fig. 6a,b). Searches almost never failed, but they often did not lead to a usable tool: {{bix_never_run_pct}}–{{iwc_never_run_pct}}% of the tools inspected in a run were never run in that run, and {{fail_a2}} calls failed because the requested tool identifier did not exist.

Failed calls added further rounds of interaction. Of {{primary_failed_calls}} failed Galaxy calls, {{fail_request}} ({{fail_request_pct}}%) were rejected before a job ran, most often because a tool schema required history context ({{fail_a1}}) or a parameter value failed validation ({{fail_a4}}). Another {{fail_execution}} ({{fail_execution_pct}}%) failed during execution, the largest class being {{fail_b2}} job errors returned without diagnostic text (Fig. 6c). UDTs were the most failure-prone operation: {{udt_call_ok}}% of {{udt_call_count}} UDT calls returned ok (Fig. 6a,d), and {{udt_prexec_nodiag_pct}}% of failed UDT jobs failed before execution without diagnostic text (Fig. 6e). Without a stated reason, agents resubmitted an identical request after {{resubmit_pct}}% of such failures, and {{resubmit_failed_pct}}% of these resubmissions failed again (Fig. 6e). In {{cb_probe_runs_pct}}% of CompBioBench Galaxy runs, agents wrote probe or preflight UDTs to diagnose the environment themselves.

These measurements identify concrete interface changes: relevance-ranked tool search with reusable inventories; history-scoped schemas that return only the parameters relevant to a request; preflight checks of UDT dependencies and dispatch with actionable failure messages; and compact responses that keep complete records retrievable rather than in the model's context. Each change has a measurable target in the archive and a quality guardrail—correct tool retrieval, fidelity of requested to resolved parameters and reporting of failure diagnostics.

## Discussion

Agents reached similar benchmark performance in Galaxy and in open-ended code, and Galaxy had fewer sporadic failures but as many persistent ones. Failure analysis points to verification, rather than knowledge, as the main bottleneck: failing analyses were seldom explained by missing domain knowledge or by the platform, and most lacked a check that would have exposed the error—an identifier assertion, a held-out evaluation, a read-level artifact test or a response to contradictory evidence. About a third of failing tasks traced to benchmark references or scoring, and these failures often persisted across attempts and environments. Benchmark curation and agent verification are therefore both prerequisites for interpreting agent accuracy.

Galaxy's resource cost was real but specific. On question-answering tasks, Galaxy runs consumed severalfold more input, much of it reread context driven by tool discovery, schema errors and failures returned without diagnostics. These are interface properties rather than inherent costs of a workbench, and on workflow tasks Galaxy did not use more total input than open-ended code. Model selection changed resource use as much as the environment did. Benchmarks that record interface activity can therefore direct workbench development to specific changes and then test whether those changes reduce tokens while preserving accuracy and provenance; the intervention study specified here will make that test.

The evidence is retrospective, and several limitations bound its interpretation. The arms differed in prompts, time budgets, runtime environments and campaign histories, including CompBioBench Galaxy runs drawn from campaigns named for wrong answers or target scores; our estimates describe assigned arms, not an isolated effect of Galaxy. The CompBioBench endpoint uses a reconstructed key and some IWC references were calibrated from agent runs. The audit covers every failing task, but its labels are AI-assisted and await blinded expert adjudication, and its tags do not test knowledge directly. Recorded tokens are not provider cost, and retained records have not yet been replayed independently or on a second Galaxy deployment.

## Methods

### Archive, populations and eligibility

This is a retrospective analysis of retained run summaries, evaluator grades, interface call records and audit notes. No new benchmark agent, Galaxy job or independent deployment was executed. Primary runs are the four shared Codex configurations in both arms, with three attempts per task and arm. Excluded Astra runs have no Galaxy counterpart; the superseded runs used a different harness. Endpoint summaries retain every assigned run with an available endpoint; UDT use in a missing trace is reported as unknown. The IWC task with incomparable arm scores is excluded from endpoints and performance–token matching but retained for interface activity. Source Data records run, task, configuration, replicate and bootstrap cluster identifiers.

The arms differ in recorded conditions. Galaxy prompts add execution policy, and no primary Galaxy–code prompt pair is identical. IWC runs had 6-h or 12-h wall-clock limits that depended on start time, with equal limits in 73 of 120 archived replicate pairs (63 of the nine-task primary population); CompBioBench code prompts stated a 120-min budget, and no budget is recorded for CompBioBench Galaxy or BixBench runs. CompBioBench Galaxy runs executed in containers and code runs on the host. CompBioBench replicate vectors are composites: 387 of 1,200 Galaxy runs and 101 of 1,300 code runs came from campaigns other than the largest in their vector, and 86 Galaxy runs came from campaigns whose names refer to wrong answers or target scores. [Authors: document the selection rule for the CompBioBench Galaxy campaigns named for wrong answers or target scores]. Exact model snapshots and complete interface commits are not uniformly preserved.

### Benchmark scores and sensitivity analysis

BixBench-Verified-50 comprises 50 binary evaluator-scored tasks with dependence within source capsules; we reuse fixed submitted-answer grades. CompBioBench comprises 100 tasks scored against a reconstructed key; its 54 score-inferred and 46 predicted references require validation with the official evaluator, and submitted and reference answers are withheld here. IWC uses nine continuous workflow-output agreement scores; ATAC-seq route references include calibration from agent runs. Scores are not pooled across benchmarks or dichotomized for IWC.

The BixBench sensitivity excludes the 15 tasks with primary audit categories C1, C2, C3 or C6. The CompBioBench sensitivity excludes every task–configuration cell in which any Galaxy replicate comes from an outcome-named campaign (66 cells), retaining 1,002 runs per arm; a campaign name flags potential selection without establishing it. IWC sensitivities exclude the three tasks with a zero-scored run, exclude the ATAC-seq task, or keep only replicate pairs with equal recorded time limits. These sensitivity populations were defined retrospectively.

### Statistical summaries and repeatability

Arm endpoints are means over eligible assigned runs, multiplied by 100 for binary percentages; differences are Galaxy minus code. Intervals are 95% percentile cluster-bootstrap intervals from 20,000 resamples (seed 20261002), resampling BixBench source capsules or tasks and retaining all configurations, replicates and arms of a sampled cluster.[@davison1997] Intervals describe clustered sampling variation within this archive, not design confounding or reference uncertainty. Model and sensitivity comparisons are exploratory; no equivalence, non-inferiority or multiplicity-adjusted claim is made.

A replicate set is one task × configuration × arm with three attempts. All-three-correct requires three accepted grades; binary discordance requires both accepted and rejected grades; IWC discordance requires a within-set agreement range greater than 0.05. Discordance ratios use matched sets and clusters. Cross-arm transitions compare the number of rejected attempts in the code and Galaxy sets of the same task and configuration. All-three-correct is a grade-based measure, not exact answer-text identity.

### UDT observations

UDT observations use the reconciled interface call table for the primary configurations. We distinguish an observed UDT call, a returned job record, a job in state ok and an ok interface return. Run-level trajectories do not infer absence from a missing trace. Run-level acceptance by trajectory is descriptive and may be confounded by task difficulty, configuration and retries.

### Failure audit

The audit covers every BixBench task with a rejected run in any archived configuration (33 tasks, including all 22 with a rejected primary run), every CompBioBench task with a run deviating from the reconstructed key (53 tasks, including all 51 with a rejected primary run), six IWC workflows with a low-agreement run and one in which near-perfect agreement concealed a changed significant-gene set. The build verifies that every BixBench and CompBioBench task with a rejected primary run is audited and that the BixBench audit equals the set of tasks with any rejected run. Census analyses use the 73 binary-benchmark tasks with a rejected primary run. Each task has one of eight primary categories and non-exclusive tags, including insufficient verification and domain knowledge. Cause groups are agent analysis (C5); benchmark, reference or provenance (C1 equivalent answer, C2 scoring artifact, C3 reference depending on an unstated choice, C6 provenance or answer exposure); Galaxy platform or wrapper (C4); and other (C7, C8). A task is persistent if any primary set was rejected in all three attempts and sporadic otherwise. Labels are task-level; run-level shares weight tasks by their rejected primary runs.

Annotations were made with AI assistance from traces, outputs and audit notes; blinded expert review with inter-rater agreement is pending. Tags are not knowledge tests, and missing reasoning is not coded as absent validation. For five illustrative cases, we located positive decision and check evidence in retained reasoning or command records and verified each source line by SHA-256 hash; contrasting runs identify a check in a sibling run without establishing that the check alone caused success. Source Data includes locators and hashes without private CompBioBench answers.

### Token measurements and model trade-offs

Input is the recorded usage field including cache reads; uncached input subtracts cached input; output is retained separately. These measures exclude unrecorded external or subagent usage and do not estimate provider cost. A paired cell is a task × configuration with three recorded usages in each arm and positive code usage. The primary arm measure is the ratio of total Galaxy to total code input over eligible cells, which reflects aggregate consumption; its interval resamples clusters with both arms. The median across cells of the ratio of three-run medians, which weights each task equally, is reported as a secondary measure.

The performance–resource comparison uses tasks with complete scores and input in all eight configuration–arm groups. A configuration is on the point-estimate frontier if no other configuration in the same benchmark and arm has both no lower mean endpoint and no greater median single-run input, with one strict improvement; a sensitivity analysis repeats this with mean input. Frontier status describes point estimates, not significant dominance. Within discordant binary sets, sibling ratios compare median input of rejected and accepted attempts; intervals crossing one do not establish equal use.

### Interface operations and failure classes

Interface analyses include Galaxy interface namespaces and exclude 307 calls to other tool servers. A call failed if the retained extractor flagged it or its client or item status was failed; this union gives {{primary_failed_calls}} failures among {{primary_interface_calls}} primary calls (7,987 among 69,505 across the archive). Failed calls were classified by ordered text rules into classes covering requests rejected before a job ran (A1–A8), job failures during execution (B1–B5) and other exceptions. Mutually exclusive UDT outcomes are an ok return, a job error with diagnostic text (standard error, standard output or a traceback), a job error without diagnostic text, or another non-ok return. Trace-level measures over the primary Galaxy traces count distinct tools inspected and never run within a run, the next call after a failed job without diagnostic text (identical or modified payload and its status), and UDTs whose identifier names a probe, preflight, smoke, sanity, render or diagnostic job. Returned characters describe response size, not tokenizer counts. Per-run actions are interface calls plus shell commands.

### Prospective token-reduction study

The planned study freezes task and input hashes, model and reasoning settings, prompts, budgets, runtime catalogue, interface commits, evaluator and answer extraction, then compares a baseline, prompt and skill changes, MCP changes and both, with randomized block order, isolated workspaces and a contemporaneous frozen code arm. Replication will be set by registered clustered power simulations. The primary outcome is input tokens per assigned attempt, retaining failures and timeouts, summarized both as reduction relative to the baseline and as Galaxy/code ratio of totals.
